# 交易记录与市场 Profile 设计

## 目标

修正跨平台双腿执行中首腿高精度成交数量与第二腿订单精度不一致造成的误报；复用现有跨平台执行会话持久化记录并在历史界面展示；增加构建期市场 Profile，让打包产物只启用明确选择的资产、周期、平台和路线。

## 约束

- 不修改成熟 MEXC↔Polymarket 旧订单记录格式、下单 IPC 或恢复状态机。
- 不在下单热路径增加余额或额外市场请求。
- 第二腿数量必须向下归一化，不能因为显示精度造成超额对冲。
- Profile 只允许缩小运行范围，不能绕过现有平台能力和实盘门禁。
- 用户密钥、订单数据和运行时设置继续保存在系统用户目录，不打包进 Profile。

## 方案

### 成交精度

在通用两腿执行状态机中为第二腿生成一个明确的订单数量。该数量按第二腿的两位数量精度向下取整，并同时用于订单请求、成交比较和回执目标数量。首腿原始成交数量继续原样记录；如果因取整产生极小尾差，在成功消息中注明但不把已完全成交的第二腿标记为恢复态。

### 交易记录

继续使用 `ExecutionSessionStore` 的版本化 `execution-sessions.json`，增加读取全部会话的能力。AppSnapshot 同时保留未完成会话和全部多平台历史；历史弹窗按来源分组显示旧订单和多平台会话，并为多平台恢复会话提供核对后标记已恢复入口。

### 市场 Profile

在 `config/market-profiles/*.json` 中保存构建配置，包含 `subjects`、`intervals`、`venues` 和 `routes`。构建脚本通过 `--profile=<id>` 校验并把选中的 Profile 复制为成品资源 `market-profile.json`；开发环境默认使用 `btc-all`。主进程启动时加载该 Profile，并在连接器创建、市场快照过滤和机会路线生成前应用统一白名单。未被 Profile 允许的平台不会启动后台页面或加入比较。

## 验证

- 单元测试覆盖首腿 `7.192`、第二腿请求/成交 `7.19` 应为 `HEDGED`，以及真实少成交 `7.18 / 7.19` 应进入恢复态。
- 执行会话存储测试覆盖读取全部记录且不改变未完成筛选。
- Profile 校验测试覆盖未知 Profile、非法周期、未知平台和不允许路线。
- `npm test`、`npm run typecheck`、`npm run build` 全部通过。
