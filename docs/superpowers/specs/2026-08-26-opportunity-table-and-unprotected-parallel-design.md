# 机会表格精简与无保护并行执行设计

## 1. 背景与目标

当前 Gate↔Kalshi 机会表格同时展示路线、方向、数量、深度、只读标记和窗口状态，右侧执行面板又重复展示相同信息，导致扫描区信息密度高但重点不突出。本次改动的目标是：

- 让表格只承担跨平台机会比较和状态扫描；
- 让右侧面板只承担选中机会的下单参数和执行结果；
- 在表格中突出显示双腿成本；
- 复用现有全局 `unprotectedExecutionEnabled`，增加 Gate↔Kalshi 的同量并行下单策略；
- 保留必要的技术安全护栏，不引入自动重试或重复订单。

## 2. 范围

### 包含

1. Gate↔Kalshi 及其他多平台机会表格的列和视觉层级调整。
2. 右侧多平台执行面板的重复信息移除。
3. 全局无保护开关在多平台执行路线上的复用。
4. 多平台无保护并行执行的回执、持久化和恢复提示。
5. 单元测试、执行策略测试和生产构建验证。

### 不包含

- 不改变 Gate、Kalshi、MEXC 或 Polymarket 的行情捕获接口。
- 不改变普通保护模式下“首腿实际成交后再提交第二腿”的顺序。
- 不增加自动重试、补单或自动对齐裸敞口。
- 不改变全局开关默认值：仍默认为关闭。

## 3. 页面设计

### 3.1 机会表格

表格列固定为：

`标的/窗口 | 第一腿 | 第二腿 | 净边际/份 | 预计净利润 | 剩余 | 状态 | 双腿成本`

- 删除“路线/方向”列；方向直接放入第一腿和第二腿单元格，例如 `Gate ↑ 0.8500`、`Kalshi ↓ 0.3500`。
- 删除“数量/深度”列；可执行份额和每腿深度只在右侧选中面板显示。
- 删除标的单元格中额外的“只读”徽标；只在状态列展示“只读观察”“双腿待确认”“行情过期”等最终状态。
- 新增最后一列“双腿成本”，使用 `allInCostPerShare`，格式为 `1.0700 / 份`，加粗并使用大号数字。
- 保持现有固定排序和自动选中行为，不因删列改变机会去重、排序或选择逻辑。

### 3.2 右侧执行面板

- 删除重复的周期状态、结算规则差异、BTC 时间窗口和“深度不足/暂不可下单”禁用按钮。
- 保留两腿平台、方向、价格、可用份额、执行份额输入、最大可执行量、每腿预计金额、成本/利润指标、条件问号和实际执行结果。
- 选中机会的上下文由左侧表格承担；右侧不再重复一整套标题和状态说明。
- 普通保护模式和无保护模式使用同一执行按钮区域。无保护打开时，按钮显示“极速无保护 · 同量双边提交”，并显示一条简短风险提示。

## 4. 无保护并行执行

### 4.1 开关与适用范围

- 继续使用 `RiskSettings.unprotectedExecutionEnabled`，设置页只保留一个全局开关。
- 默认关闭；打开仍需要用户明确确认。
- 在人工监督模式下可用于旧 MEXC↔Polymarket 路线和新的 Gate/Kalshi 多平台路线。
- 自动开单不会因该开关绕过现有自动执行门禁，除非后续另行设计自动模式策略。

### 4.2 发送语义

无保护模式下，程序根据用户输入的目标份额 `Q`，在同一个执行时刻启动两条下单任务：

1. Gate 页面下单任务提交 `Q` 份。
2. Kalshi API 下单任务提交 `Q` 份。

两条任务并行启动，不等待 Gate 的成交回读，不根据首腿真实成交数量调整第二腿，不检查滑点、收益率、结算信号或行情新鲜度。这表示“目标份额相同”，不保证“最终成交份额相同”。

仍保留以下硬性技术检查：

- 市场 ID、周期和方向匹配；
- Gate 页面、Kalshi 凭据和对应实盘开关就绪；
- Gate 最低 5 USDT、Kalshi 最低份额和用户输入数量有效；
- 同一时间只有一组双腿执行；
- 网络超时或结果未知时不自动重试。

并行策略只发出用户明确要求的两条订单请求，不复制请求、不重放请求、不额外轮询下单接口。

### 4.3 回执和恢复

新增明确的 `UNPROTECTED_SUBMITTED`（无保护双边已提交）结果语义：

- 两个平台都返回明确的提交/成交结果：记录两边订单号，状态为 `UNPROTECTED_SUBMITTED`，显示“无保护双边已提交，成交待核对”；
- 任一平台失败、超时或返回未知订单：进入恢复/核对态，记录已知订单号和错误，不自动重发；
- 两边实际成交量不同：只记录差异和风险，不执行自动补单或数量对齐；
- 普通保护模式仍使用现有 `SEQUENTIAL_FILL_THEN_HEDGE`，并继续按首腿实际成交量对齐第二腿。

执行会话持久化需要保存：策略类型、目标份额、两腿提交时间、两腿订单号、两腿返回状态、已知成交量和差异说明。历史列表要能区分普通对冲完成、无保护双边已提交和需要人工核对。

## 5. 数据流与错误处理

1. UI 从全局设置读取无保护开关，并将当前目标份额发送给主进程。
2. 主进程在执行入口做硬性技术检查，然后选择普通顺序策略或无保护并行策略。
3. 并行策略先准备两个适配器调用，再同时启动两次 `submitOrder`；不得先等待其中一条任务完成。
4. 使用 `Promise.allSettled` 收集两个结果，分别写入执行会话；任一结果不确定时进入恢复/核对态。
5. 结果写入现有执行历史和日志，UI 仅展示摘要，详细响应继续保存在本地脱敏记录中。

## 6. 测试与验收

- 表格渲染测试确认目标列存在，路线/方向、数量/深度和右侧重复禁用按钮不存在。
- 无保护策略测试确认两条 `submitOrder` 在任一条完成前都已启动，且两条请求目标份额都为 `Q`。
- 测试确认无保护模式不调用首腿成交等待，也不修改第二腿数量。
- 测试覆盖一边失败、一边超时、两边订单号已返回但成交量不同的恢复结果。
- 回归普通保护模式：首腿成交后才发送第二腿，且原有精度对齐测试继续通过。
- 全量 `npm test`、`npm run build` 和 `git diff --check` 必须通过。

## 7. 风险与回滚

- 无保护模式可能产生两边实际成交量不一致的裸敞口，因此默认关闭、需要显式确认，并明确展示“成交待核对”。
- 并行策略只在新开关打开时生效；关闭开关即可回到现有顺序执行，不需要迁移旧订单。
- 若并行策略回执或平台接口出现兼容问题，可保留页面精简改动并将策略选择回退到 `SEQUENTIAL_FILL_THEN_HEDGE`。
